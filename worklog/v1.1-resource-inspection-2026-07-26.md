## 3. 实现内容

### 3.1 分层、只读采集

- `InspectionProvider` 新增冻结契约定义的 `collect_resources(request)`。
- Kubernetes Provider 将状态采集与证据采集分层：
  - `status` 只读取资源状态和可选 Metrics，不读 Event、日志。
  - `evidence` 只允许读取请求中显式给出的 Pod 目标，并按开关读取 Event/日志。
- 每次采集使用 `ProviderCollectionRequest.thresholds` 的不可变快照；共享 Provider 不保存可变策略。
- 每次采集使用独立的 API 计数、时间、引用缓存；Pod 重启采样通过带锁的共享存储维护，避免并发运行互相覆盖请求级状态。
- 采集错误按检查项和资源范围隔离为 `ProviderCollectionFailure`，不把采集失败伪装成健康。
- 集群范围判定按实际发现的 namespace 拆分 Coverage；某一 namespace 采集失败不会将其他 namespace 一并判为失败。

### 3.2 资源采集与判定

- 工作负载：Deployment、StatefulSet、DaemonSet、Job、CronJob。
  - 支持期望副本为 0、Deployment 暂停、CronJob suspended、Job 完成等合法状态。
  - 检查发布停滞、副本不足、Job 明确失败、长时间未完成和 CronJob 错过调度。
  - Cron 支持标准五字段、列表/范围/步长、月份/星期英文名称、合法宏和 `timeZone`；非法表达式显式返回失败，不猜测健康。
- Pod：
  - 检查 Running 但 Ready=False、init container、ImagePullBackOff、terminated/last terminated、Unschedulable、长时间 Terminating、窗口内重启增量、探针和卷挂载 Warning Event。
  - 通过 `ownerReferences` 建立 Pod 与 Deployment/StatefulSet/DaemonSet/Job 的关系。
  - 对 Pod 实际引用的 ConfigMap、Secret、ServiceAccount、imagePullSecret、PVC 做定点存在性检查；不批量读取 Secret/ConfigMap。
- Service/EndpointSlice：
  - 合并同一 Service 的全部 EndpointSlice。
  - `ready=null` 按 Kubernetes 语义视为可用。
  - 支持 selectorless Service 的手工 EndpointSlice；ExternalName 不做 Endpoint 健康判断。
  - 被 Ingress 引用且无 Ready Endpoint 时提升严重性。
- Ingress：
  - 校验 Service 是否存在、backend 端口、Ready Endpoint 和显式 IngressClass。
  - 结果明确命名为“配置链路”，不使用 `loadBalancer` 状态声称外部网络可达。
  - Resource Backend 标记为当前版本不适用，不误报 Service 缺失。
- TLS：
  - 只读取 Ingress 实际引用的 TLS Secret。
  - 内存中校验证书格式、有效期、尚未生效、SAN（通配符只匹配一层）和证书/私钥匹配。
  - Secret data 使用后立即清除引用；DTO、Evidence、日志均不包含证书原文或私钥。
- 存储：
  - 检查 PVC Pending/Lost、PV Failed、长期 Released、StorageClass binding mode。
  - `WaitForFirstConsumer` 且没有消费 Pod 时不误报；Retain/Released 仅生成 info 清理提示。
- Node 与 Metrics：
  - 检查 Ready、Memory/Disk/PID Pressure、NetworkUnavailable。
  - 采集 cordon、taint、allocatable，并汇总 Pod requests（含 init container 最大值与 Pod overhead）。
  - `metrics.k8s.io` 为可选能力，计算 CPU/内存 usage、request/limit 比率和陈旧样本；无 limit 不生成伪百分比。
- 必需组件：
  - 按配置的 namespace、kind 和 label selector 从真实工作负载发现。
  - 只有启用的必需组件缺失才告警；不按名称猜测可选控制面组件。

### 3.3 契约输出和兼容

- 所有资源判定输出冻结的 `CheckEvaluation`、`Coverage` 和 `IssueCandidate`。
- 每个结果使用实际 `InspectionScope` 和 `build_inspection_scope_key()`。
- `Coverage.issue_count` 与候选问题数量一致；失败检查不带伪造的问题候选。
- Mock Provider 覆盖正常、异常及局部失败数据；评估器测试覆盖 skipped。
- 保留 v1.0 Provider 接口，并修正以下历史假健康：
  - Running 但 Ready=False 的 Pod 判为异常。
  - Service 使用真实 EndpointSlice，而非固定 healthy。
  - Ingress 使用配置链路检查，而非 loadBalancer 是否为空。
  - TLS 改为定点 Secret 检查，取消 namespace 全量 Secret 列表。
  - 历史日志摘要限制为最多 5 行。

### 3.4 Provider 职责拆分

原 `kubernetes_collection.py` 为约 2161 行。收口后为 1869 行，保留 Kubernetes API 编排、资源关系建立、脱敏 Observation 和证据预算控制；以下高风险独立职责已移出：

- `kubernetes_cron.py`：Cron 表达式与时区解析。
- `kubernetes_quantities.py`：CPU/内存 quantity 和 Pod 调度资源汇总。
- `kubernetes_restart_state.py`：线程安全、自动清理的重启采样状态。
- `kubernetes_tls.py`：TLS Secret 内存解析、SAN 与密钥匹配。

资源健康规则没有放回 Provider，而是拆为 workload、Pod、network/TLS、storage、node/metrics 和公共构建模块。这样采集与判定可分别测试，也避免解析器和跨运行状态继续堆积在 API 编排类中。

## 4. 关键设计决定

### 4.1 新增 Kubernetes API 和 RBAC

新增或扩展的只读 API：

- Core：Namespace、Node、Pod、Service、Event、PVC、PV 的 `get/list`。
- Core 定点引用：ServiceAccount、Secret、ConfigMap 的 `get`。
- Pod 日志：`pods/log get`，仅证据层显式目标使用。
- Apps：Deployment、StatefulSet、DaemonSet、ReplicaSet 的 `get/list`。
- Batch：Job、CronJob 的 `get/list`。
- Networking：Ingress、IngressClass 的 `get/list`。
- Discovery：EndpointSlice 的 `get/list`。
- Storage：StorageClass 的 `get/list`。
- Metrics：Pod、Node metrics 的 `get/list`。
- Version API：读取 Kubernetes 服务端版本。

RBAC 不包含 `create/update/patch/delete/watch`。Secret、ConfigMap 只有 `get`；非 TLS Secret 只做存在性检查，不解析 data。

### 4.2 skipped 条件

以下情况返回明确 `skipped`，不显示为健康：

- Kubernetes 版本未读取，或版本不在商用支持范围 1.34～1.36。
- 未配置启用的必需组件策略。
- 当前范围没有对应的工作负载、Pod、Service、Ingress、PVC/PV、Node。
- Service 范围内仅有 ExternalName，或仅有“无 selector、无手工 EndpointSlice、未被 Ingress 引用”的 Service。
- Ingress 仅使用 Resource Backend，当前版本不判断非 Service 后端链路。
- 当前范围没有 Ingress TLS 引用。
- Metrics API 不可用、没有当前样本或样本陈旧。

以下是合法/预期状态，不生成问题，但检查仍可为 `passed`：

- Deployment/StatefulSet 期望副本为 0，Deployment 暂停。
- CronJob suspended。
- Completed Job/Pod。
- `WaitForFirstConsumer` PVC 没有消费 Pod。
- Node cordon 或普通 taint（保留为事实，不单独当故障）。
- 未配置 CPU/内存 limit。
- Normal Event 和超过事件窗口的 Warning Event。

### 4.3 API 与日志预算

- 状态层：日志读取数和日志字节数必须为 0，也不读取 Event。
- 证据层：显式资源目标最多 1000 个。
- 默认日志目标 Pod 上限：200。
- 默认每容器 tail：1000 行。
- 默认每 Pod 日志读取上限：1 MiB。
- 默认单次日志总量上限：20 MiB。
- 超限时停止读取并设置截断标记；原始日志仅作为临时 matcher 输入，返回 DTO 只含摘要事实，不含完整日志。
- Event 只输出 type、reason、count、时间等结构化事实；原始 message 不进入 Evidence。
- `ProviderCollectionResult` 记录 Kubernetes API 调用数、日志 Pod 数、日志字节数和耗时。
- namespace 默认并发 3、上限 10 由冻结请求契约和调度层控制；本 Provider 的单请求执行不自行启动额外线程。

## 5. 未完成或待确认

以下检查因没有可靠数据或超出 v1.1.0 安全边界而明确不实现：

- 不使用 Pod exec，不检查主机 systemd、containerd、kubelet 进程状态。
- 不做 Ingress/Service 的集群外真实连通性探测；只判断 Kubernetes 配置链路。
- 不在没有监控数据时推断卷文件系统使用率。
- 不按资源名称猜测未暴露的控制面进程健康。
- 不根据时间接近关系自动推断唯一根因。
- 不解析非 TLS Secret 内容。
- 不读取全部正常 Pod 的日志，也不持久化完整日志。
- Resource Backend 的下游健康暂不判断。
- Metrics 连续周期状态由后续调度/Issue 生命周期模块按历史运行补充；Provider 只输出当前样本和契约字段，不在进程内伪造历史趋势。

## 7. 风险

- 未连接真实 Kubernetes 1.34、1.35、1.36 集群做端到端验证；当前为 Kubernetes client fixture 和 API 形状测试。
- Metrics 高使用率要求“连续多个定时周期”；当前 Provider 正确不以单次样本告警，依赖下游运行历史补充连续计数。
- 集群范围一次性遍历对象量可能较大；已经有 API/日志计数与日志硬预算，但状态资源列表仍需后续在大集群压测中校准。
- Python 环境缺少 `ruff`，本次使用编译、测试和 `git diff --check` 代替基础校验。
