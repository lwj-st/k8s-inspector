## 3. 开工计划

1. 盘点旧 Provider namespace、批量、状态和诊断调用，建立“允许读日志/禁止读日志”矩阵。
2. 为旧 namespace Provider API 增加显式 `include_logs` 参数且默认 `false`；状态、批量和轻量发现始终传 `false`，主动日志页才传 `true`。
3. 新增轻量 Pod 名单发现契约与 API，只读取 Pod 元数据，不创建 InspectionRun/InspectionRecord，不读取 Event/Log。
4. 诊断模板先检查是否存在启用的 `log_keyword` 条件；无日志条件时禁止读日志，有日志条件时只采集模板明确目标，并复用 `CollectionLimits`。

6. 增加定向测试，覆盖状态/批量/非日志模板零日志调用、日志模板定点采集、轻量发现无副作用、超限零日志调用和 Settings 兼容。
7. 对诊断日志执行“内存原文匹配、公开响应与数据库统一脱敏和限长”，覆盖常见凭证、飞书 Webhook 和私钥。
8. 运行定向回归、编译和边界审计，记录必须交给 Agent04/前端的准确接线点。

## 5. 初始契约判断

- `CollectionLimits.max_log_pods` 已存在，默认 200、范围 1 至 1000；缺口是没有进入 `InspectionPolicySettings` 和 Settings 持久化快照。
- 现有 Settings 采用数据库 JSON 保存完整 `InspectionPolicySettings`，因此该上限应进入同一策略对象；不需要新增 Helm/env 配置，避免两套来源不一致。
- 现有巡检主链仍有固定 200 门禁，由 Agent04 维护；本 Agent只提供 `policy_snapshot.max_log_pods` 和 Provider/诊断执行边界，待总调度批准后由 Agent04完成接线。
- 总调度兼容复核后冻结：在 `NamespaceInspectionRequest` 精确追加
  `include_logs: bool = true`，旧 v1.0 客户端省略字段时保持受限日志证据；
  v1.1 状态页必须显式传 `false`，日志页显式传 `true`。Provider 内部方法默认
  仍为 `false`，避免新内部调用隐式读取日志；不修改其他已有请求/响应字段。
- 质量复核发现诊断响应和 `DiagnosisRecord` 会泄漏日志中的凭证；匹配阶段仍需内存原文，但响应和落库必须使用同一份递归脱敏后的 DTO。

## 6. 实施记录

### 6.1 Provider 日志边界

- `run_namespace_inspection()` 增加关键字参数
  `include_logs=false/limits=None`；Provider 内部默认不读日志。
- Kubernetes Provider 在 `include_logs=false` 时不调用 Pod Log 和 Event API，
  `log_summary/previous_log_summary` 为空；`include_logs=true` 才进入受限采集。
- 新增只在内存存在的 `TemporaryPodLogCollection`，按
  `max_log_pods/max_container_log_lines/max_log_bytes_per_pod/max_total_log_bytes`
  约束当前日志和上次终止日志；超 Pod 上限时在任何 Pod/Log 读取前拒绝。
- cluster Provider 内部同样默认 `include_logs=false`；公开旧接口默认 true
  保持兼容，v1.1 状态页显式 false。
- Mock Provider 与 Kubernetes Provider 使用相同开关语义。

### 6.2 轻量 Pod 发现

- 新增
  `GET /api/v1/discovery/namespaces/{namespace}/pods?label_selector=...`。
- 响应固定为：
  `{namespace,label_selector,executed_at,pod_count,pods:[{name,labels}]}`。
- 该路径只调用 Pod list，并只读取 metadata 中的 name/labels；不调用巡检服务，
  不创建 InspectionRecord/InspectionRun，不读取 Event/Log。
- namespace 日志预检复用该接口的准确 Pod 数，不再通过标签候选或名称空间缓存估算；
  Provider 实际列表变化导致的二次超限也统一转换为 422。

### 6.3 模板诊断分层

- 每个模板先执行 `include_logs=false` 的状态采集，再按模板
  label selector 和 pod_name_pattern 得到明确 Pod 目标。
- 没有启用 `log_keyword` 条件时不调用日志采集。
- 有日志条件时只读取模板目标；同一次 diagnosis 的多个模板共享
  `CollectionLimits`、目标去重缓存和总字节预算，不重复读取相同 Pod。
- 日志原文只在临时内存对象中参与匹配，不进入 Provider DTO。

### 6.4 可配置运行上限

- `InspectionPolicySettings.max_log_pods` 默认 200、范围 1..1000。
- Settings GET 始终返回完整值；PUT 随现有 `inspection_policy` JSON 持久化；
  老数据自动补默认值，老 PUT 省略策略时保留当前值。
- 未新增 Helm/env 配置，因为现有产品已将巡检运行策略持久化到 Settings；
  避免出现数据库与环境变量两套冲突来源。
- namespace/cluster 仅在 `include_logs=true` 时执行动态门禁；batch 固定 false，
  不因 Pod 数量大而拒绝状态巡检；scheduled Run 的 `CollectionLimits` 使用同一
  policy snapshot 的 `max_log_pods`。

### 6.5 公开兼容与敏感信息

- `NamespaceInspectionRequest.include_logs` 公开默认 true，保持 v1.0 旧客户端
  省略字段时仍返回受限日志证据；显式 false 为零日志状态模式。
- cluster 公开接口使用 query `include_logs`，默认 true；显式 false 为状态模式。
- 新增纯函数 `payload_sanitizer`：公开版保留 dict/list/tuple 结构并递归脱敏、
  限长；持久化版额外移除 raw-log key 并写入截断元数据。
- 覆盖 password/passwd、各类 token/secret、API Key、Bearer、Cookie、
  Authorization、飞书 Webhook 和私钥；保留非敏感 ERROR 等排障信息。
- diagnosis 使用内存原文完成匹配后，对 API 和 DiagnosisRecord 分别清洗；
  InspectionRecord 保持冻结的旧 metadata 外形
  `{raw_logs_removed,truncated}`。

### 6.6 前端准确接线契约

- 单 Pod 下拉框必须使用轻量 Pod discovery，不能用 namespace inspection 发现。
- 状态页和批量显式 `include_logs=false`；namespace/selector 日志页显式 true；
  cluster 状态请求 query 显式 false。
- 门禁提示读取 Settings 的 `inspection_policy.max_log_pods`，不得硬编码 200。
- 本 Agent 不修改前端；上述接线已交给前端责任 Agent。
