## 4. 实现内容

### 数据库与 ORM

- 建立 v1.0.0 Alembic baseline：空库执行 baseline 后继续升级；已有、未版本化的 v1.0.0 数据库先核对七张基线表，再 stamp baseline。
- 建立 v1.1.0 固定 revision；migration 使用 revision 内冻结的 Table 定义，不依赖未来可能变化的 ORM metadata。
- 建立 Issue、IssueEvent、InspectionRun、InspectionCheckResult、InspectionPlan、NotificationChannel、NotificationDelivery、ResourceMetricState、SecurityAuditLog、AdminSession 和关联表。
- `InspectionCheckResult` 唯一约束严格为 `(run_id, check_code, scope_key)`。
- v1.1.0 初始化不再调用 `Base.metadata.create_all()` 或临时 `PRAGMA + ALTER TABLE`；应用、标准 Alembic CLI、CI 和 Helm initContainer 复用 `backend/app/db/migrations/`。
- 旧版 `system_settings.api_key` 升级时加密到 `api_key_encrypted` 并清空明文列；downgrade 时使用同一密钥恢复旧列，支持回滚旧应用。

### 单管理员安全

- 使用 `argon2-cffi` 验证预置 Argon2id 密码哈希，不保存或接收明文配置密码。
- 登录创建 48 字节随机 Cookie Session；Cookie 为 HttpOnly、SameSite=Strict，Secure 可配置且生产强制。
- 数据库只保存使用 Session Secret 计算的 HMAC-SHA256 Token 哈希，不保存原始 Token。
- 默认空闲 30 分钟、绝对 8 小时；访问时续空闲时间但不超过绝对时间；过期和退出均服务端撤销。
- 全部受保护写 API 统一校验 `X-CSRF-Token`；后续 Agent 新增写路由无需重复实现。
- 同一客户端 IP 在默认 10 分钟内失败 5 次后返回 429；来源只使用连接地址，不信任请求头伪造地址。
- 登录成功、失败、限流、退出和 Settings 修改写安全审计；审计字段使用 allowlist，不包含密码、Cookie、Token、完整 Webhook 或 API Key。

### 加密与出站安全基础

- 使用 `cryptography.Fernet` 认证加密，密文绑定用途；支持 `llm_api_key`、Webhook 地址和飞书签名密钥等调用方定义用途。
- 缺密钥、密钥格式错误、错误密钥、用途不匹配和密文损坏均返回不包含敏感值的明确错误。
- 实现 Webhook 地址的 scheme、userinfo、端口、Host 注入、DNS 全部 A/AAAA 地址、Host/CIDR allowlist、回环、链路本地、私网、元数据、保留地址校验。
- 出站校验返回 `ValidatedOutboundTarget`，而不是裸 tuple。调用方必须把连接固定到本次 `resolved_addresses`，保留 hostname 作为 HTTP Host/TLS SNI，并用 `require_allowed_peer()` 校验实际 socket peer；禁止再把原 URL 交给会二次 DNS 解析的默认客户端。
- 可信详情页基础地址只来自静态配置；生产要求 HTTPS，拒绝 userinfo、query、fragment 和控制字符。
- 本 Agent 只提供飞书 Webhook/签名密钥的加密存储基础，不实现通知发送、飞书消息转换或应用机器人。

### 健康状态与生命周期扩展

- `/health/live` 只报告进程和版本，不依赖数据库、Kubernetes API、Metrics 或 Webhook。
- `/health/ready` 检查 migration head、数据库、平台初始化、生产安全配置和 lifespan hook。
- `/api/v1/system/status` 提供数据库/schema、Provider、配置和 Agent 04 可扩展的调度、Metrics、通知、最近巡检状态占位；未知能力明确显示 unavailable，不伪造健康。
- 系统总状态按冻结语义聚合：存在 not-ready 原因优先返回 `not_ready`；否则任一组件非 `ok` 返回 `degraded`；全部组件为 `ok` 才返回 `healthy`。
- 提供线程安全的 `ComponentStatusRegistry`；Agent 04/Provider/编排只能用冻结 `SystemComponentStatus` 更新 scheduler、notifications、last_inspection、kubernetes_api、metrics_api 和 Kubernetes version，不需要修改 security 文件。
- 提供异步/同步 start/stop hook 注册；migration 和安全初始化成功后才启动，stop 逆序，start 失败会清理已启动 hook 并阻断 Ready，错误响应不暴露内部异常正文。
- Provider 初始化失败不会回退 Mock 或退出进程：liveness 保持，readiness 失败，系统状态显示 provider=failed，依赖 Provider 的路由统一返回 503。
- HTTPException、Pydantic 422 和未处理异常统一转换为冻结 `ApiError`；middleware 只接受 1 至 128 字符且符合 `[A-Za-z0-9][A-Za-z0-9._:-]*` 的 request_id，超长、空格、斜线、CR/LF 或其他非法值统一替换为 UUID，再写入 request.state、响应体、响应头和安全审计。错误 details 永远为空，不回显输入或原始异常。

### Settings 兼容

- `GET /api/v1/settings` 始终返回完整 `inspection_policy`。
- 老客户端 PUT 未携带 `inspection_policy` 时保留当前策略；显式 `null` 返回 422。
- API Key 只返回 `********` 或 `null`；收到掩码时保留，收到新值时加密，收到 null 时清除。

### Helm

- 持久化部署增加同应用镜像的 `database-migration` initContainer，migration 失败会阻止主容器启动。
- Deployment 模板对 `replicaCount != 1` 直接 `fail`，把 SQLite 单写和进程内调度前提变为部署硬门禁。
- 主容器在持久化生产部署中 `AUTO_MIGRATE=false`；无持久化 CI/开发部署由主进程对其临时文件系统迁移。
- readiness 改为 `/health/ready`，liveness 改为 `/health/live`。
- Secret 增加管理员、Session 和加密配置；ConfigMap 增加环境、集群标识、Session、限流、可信详情地址和 Webhook allowlist。

## 5. 关键设计决定

1. migration 放在 Python 包内，是为了兼容当前 Dockerfile 只复制 `backend/app` 的事实。wheel 内容检查确认 initContainer 镜像中包含同一 `env.py` 和两条 revision。
2. migration 失败后不把 Alembic 版本标记为 head。SQLite `ADD COLUMN` 采用可重试检查；补齐密钥后可继续升级。
3. 生产错误配置不通过降级为匿名访问规避；探针仍可匿名访问，其他 API 返回 401，Ready 返回具体但脱敏的配置原因。
4. NotificationChannel 使用内部 `deleted_at` 软删除列；Delivery 的 channel_id 保持非空并使用 RESTRICT，未增加冻结 DTO 之外的 channel_name 字段，满足历史投递保留和契约一致性要求。
5. 依赖固定版本，避免镜像每次构建解析到不同实现：

| 依赖 | 固定版本 | Python | 许可证 | 用途与镜像影响 |
|---|---:|---|---|---|
| Alembic | 1.18.5 | >=3.10 | MIT | SQLite migration；纯 Python |
| cryptography | 49.0.0 | >=3.9 | Apache-2.0 OR BSD-3-Clause | Fernet/TLS；PyPI 提供 CPython 3.11 manylinux amd64/arm64 wheel |
| argon2-cffi | 25.1.0 | >=3.8 | MIT | Argon2id 校验；bindings 提供平台 wheel |
| HTTPX | 0.28.1 | >=3.8 | BSD-3-Clause | Agent 04 Webhook；从 dev 提升为 runtime |
| APScheduler | 3.11.3 | >=3.8 | MIT | Agent 04 单进程调度；固定 3.x，避免 4.x API 变化 |

版本和许可证来源复核了 PyPI 项目元数据；本机实际测试版本与上述固定版本一致。未引入飞书 SDK、外部数据库、队列或 Prometheus。

## 7. 升级、备份与回退方案

### 升级前

1. 停止旧应用写入，确认只有一个副本。
2. 对 SQLite 文件执行文件级备份，并记录原文件权限、属主、大小和 SHA-256。
3. 使用 `PRAGMA integrity_check` 检查备份和源库。
4. 准备管理员 Argon2id 密码哈希、至少 32 字符 Session Secret、Fernet Key；生产还需可信详情 URL 和 Webhook allowlist。
5. 加密密钥必须独立备份；丢失密钥后不能恢复已有 LLM/Webhook/飞书签名配置。

### 升级

1. Helm initContainer 执行 `python -m app.db.migrate upgrade`。
2. initContainer 成功后主容器启动；访问 `/health/ready` 确认 `ready=true`。
3. 登录并检查 `/api/v1/system/status` 中 schema 为 `v110_platform`。
4. 验证原模板、白名单、关键字、历史巡检仍可读；验证 API Key 只显示掩码。

### 回退

首选整库回退：停止 v1.1.0，保留失败现场副本，恢复升级前 SQLite 备份，再部署 v1.0.0。

若必须就地回退：

1. 停止 v1.1.0 所有进程并备份当前数据库。
2. 保持同一 `CONFIG_ENCRYPTION_KEY`，执行 `python -m app.db.migrate downgrade --revision v100_baseline`。
3. downgrade 会把加密 LLM API Key 恢复到 v1.0.0 明文列并删除 v1.1.0 新表；v1.1.0 新增 Issue/Plan/Delivery 数据不会被旧版保留。
4. 执行 `PRAGMA integrity_check` 后部署 v1.0.0。

不得在应用仍运行时复制 SQLite 文件或执行 downgrade。

## 8. 风险与后续复核

- 当前 CI 环境使用非持久化 SQLite，因此 Helm 渲染为主进程自动迁移；正式持久化部署才启用 initContainer。质量 Agent 需在真实 PVC 场景验证 initContainer 失败阻断。
- Chart 版本和 appVersion 仍由质量 Agent 按职责更新；ConfigMap 已读取 `.Chart.AppVersion`。
- 当前环境没有独立软件成分漏洞扫描器；固定版本、许可证和多架构 wheel 已复核，但发布前仍需质量 Agent 在最终镜像运行组织要求的 CVE/SBOM 扫描。
- Agent 04 必须复用 `SensitiveValueCipher`、`ComponentStatusRegistry`、`validate_outbound_target()` 和 lifespan hook；每次重试前重新做 DNS/目标校验，HTTPX 必须 `follow_redirects=false`。网络传输必须固定到 `ValidatedOutboundTarget.resolved_addresses` 并校验实际 peer；不得校验后让 HTTPX 对原 host 再次任意解析。
- Agent 04 删除通知渠道时应设置 `deleted_at`，不得物理删除有历史 Delivery 的渠道。
