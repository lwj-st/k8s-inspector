## 3. 实现内容

### Issue 与 Run

- 使用冻结的 SHA-256 fingerprint builder，完成首次发现、重复观察、严重程度升级、重开、恢复和确认。
- 使用 `IssueScopeMembership` active 语义处理多 scope：命中时激活；成功检查缺失时只失活当前 scope；仅无其他 active membership 才恢复。
- failed/skipped Coverage 不失活 membership、不恢复 Issue。
- 恢复 Issue 同样写入本轮 `inspection_run_issues`，Run 的 `issue_ids` 包含 opened/observed/recovered。
- Issue 列表实现 priority/duration/last_changed 全结果集排序后分页；时间线独立分页。
- Run 持久化 scoped `InspectionCheckResult`；顶层 Coverage 按 check_code 汇总，不把多个 namespace 的同名检查原样重复塞入摘要。
- namespace 采集异常生成显式 `inspection.scope=failed`，单 namespace 失败不终止其他范围；全失败 Run 带受控 error_code/error_message。
- 同一次运行只读取一次 `InspectionPolicySettings`，同一快照的 thresholds 同时传给 Provider 和 evaluator，namespace 并发取同一快照的 `namespace_concurrency`。
- ResourceMetricState 只保存最新样本；仅 scheduled 周期更新连续超阈值次数，达到配置周期后生成资源使用 Issue。
- 手动 v1.0 巡检响应以向后兼容方式追加真实 `issues/coverage`，并关联同一 InspectionRecord。
- cluster/namespace/batch/pod/通用手动入口均把应用的 ComponentStatusRegistry 传给统一执行服务；service 直接调用仍可省略该可选参数，手动 Run 后系统状态会更新 last_inspection。
- scheduler 启动会按 `finished_at / created_at / id` 从持久化 Run 安全恢复 last_inspection；queued/running 显示为执行中的 degraded，重启后不会误报“暂无巡检”。
- 仅 `provider_mode=kubernetes` 的真实版本观察可更新 Kubernetes API/版本状态；版本权限失败会结合业务观察区分 degraded 与 failed，Mock Provider 明确保持 unavailable。
- 所有旧手动巡检入口在读取 Pod 日志和创建 InspectionRecord/Run 前执行硬门禁：集群按异常 Pod、Namespace/标签按目标 Pod、批量按目标 Namespace 总 Pod、单 Pod 按 1 预估，超过固定上限 200 返回受控 422 并提示“请缩小范围”。当前冻结配置契约无运行时配置项，因此未擅自扩改 schema/config/deploy。
- 公共巡检响应统一深拷贝后递归脱敏，保留完整字段结构和非敏感错误摘要；password/passwd/token/secret/api-key/Bearer、飞书 Webhook 与私钥在任意嵌套日志、命中上下文、事件和 describe 中均不回传。
- InspectionRecord 入库走独立的更严格清洗 DTO：移除完整容器日志字段，受限摘要/命中上下文脱敏和限长，截断带持久化标记。
- 巡检响应与 InspectionRecord 已改为复用共享 `payload_sanitizer`；InspectionRecord 对外保留 v1.0 两字段清洗 metadata 兼容形状，敏感值脱敏计入旧 `truncated` 语义。
- IssueCandidate 在生命周期写库前清洗 summary/reason/suggestion 与完整 Evidence 结构，ack note 同样先清洗；Run coverage 和 CheckResult 外部文本写库前清洗。
- Issue/list/timeline 与 Run list/detail 查询转换层再次防御性清洗，可安全读取历史脏数据；通知继续保留自身二次清洗，不删除 Evidence 规避风险。
- Issue/Evidence 继续先经过冻结 Pydantic 契约，单 Issue 64 KiB 上限不能被 ORM 写入旁路。

### 计划与调度

- APScheduler 通过平台 lifespan hook 启停，不修改 `main.py`。
- `POST /inspection-plans/{id}/run` 先持久化 `queued` Run 和 InspectionRecord，立即返回 202；后台 DateJob 接管同一 Run，不创建第二条记录。
- 同计划 queued/running 均禁止重入；进程内计划锁与数据库状态双重检查。
- 应用重启把遗留 running 标记 interrupted，并恢复 queued Run；计划 missed run 使用 coalesce，只补最近一次。
- queued 恢复任务在 scheduler 挂入 app state 并启动后执行，消除启动竞态；锁冲突使用 1 秒退避并复用同一 job id。
- 计划的 `include_template_matching` 为 true 时复用现有模板匹配服务，结果写入 `template.matching` Coverage；不默认拉取全部正常 Pod 日志。
- 每日清理使用任务启动时的 retention 快照；开放 Issue、queued/running Run 和带 active membership 的 Issue 不清理。

### 通知

- 通知渠道 CRUD 使用 `SensitiveValueCipher` 加密 Webhook 和签名密钥，API 永远只返回脱敏 endpoint 和是否配置 Secret。
- 删除渠道使用 `deleted_at` 软删除，不删除历史 Delivery。
- 通用 Webhook 与飞书发送每次重试都重新执行 DNS/SSRF 校验；连接固定到已验证 IP，保留 Host/TLS SNI、禁止重定向、校验实际 peer，并在同一验证结果内安全回退备用 IP。
- 正式投递最多三次；连接测试同步只尝试一次，使用 `notification_test/is_test=true`，不创建 Issue。
- 飞书仅官方 V2 群自定义机器人单向通知：非交互卡片、文本降级、可选签名、30 KiB 安全裁剪、critical 才允许且配置开启后才 @all。
- 不存在飞书应用机器人、消息接收、事件回调、卡片按钮或远程操作入口。
- 抖动达到阈值时用一次 flapping 替代普通 opened/recovered；30 分钟冷却内后续开闭写 `suppressed` Delivery，severity escalation 不被抑制，冷却后恢复普通通知。
- 按 PRD 默认不为 info 的 opened/reopened/recovered 创建 Delivery；info 升级到 warning/critical 的 severity escalation 正常通知。
- 通知适配、投递/重试和安全 transport 已拆分，避免单文件同时承担全部职责。
- 通知消息只取结构化 Evidence 摘要，并执行常见凭证、私钥和 Webhook 路径脱敏；详情地址只来自可信配置。

## 4. 关键设计决定

1. fingerprint 只调用冻结 `build_issue_fingerprint()`；文案、severity、时间和 UID 不参与去重。
2. 单一 fingerprint 可以被多个 scope 观察，因此不在 Issue 保存单一 scope_key；恢复完全依赖 active membership。
3. Run 顶层 Coverage 是按 check_code 的摘要，真实 scope 只保存在 `InspectionCheckResult`，避免跨 namespace 信息覆盖。
4. SQLite、进程内 Scheduler 和锁都建立在单副本前提上；Helm 的单副本硬门禁由 Agent03 提供。
5. queued Run 是手动触发与后台执行之间的持久化交接点；后台只能接管 queued 状态且使用原 Run ID。
6. 通知 transport 不把校验后的原 URL交回默认 DNS 客户端；每次尝试重新校验并连接本次验证 IP。
7. 飞书签名和 Webhook 都只在发送瞬间解密到内存，不写 Delivery、审计或响应。
8. 连接测试的同步等待上限是一轮渠道 timeout；正式事件才执行最多三轮。
